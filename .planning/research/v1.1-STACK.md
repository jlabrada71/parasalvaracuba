## 1. Markdown Editor Library

### Recommendation: Tiptap 3.20+

**Version:** `@tiptap/vue-3@^3.20.5` (latest as of March 2026)

**Why Tiptap over alternatives:**

| Criterion | Tiptap 3.20 | md-editor-v3 | Lexical | markdown-it |
|-----------|------------|-------------|---------|-------------|
| **Vue 3 Support** | Official + native | Vue component | Community pkg | Library only |
| **Markdown parsing** | Bidirectional | Preview-focused | Excellent | Parsing only |
| **Headless UI** | Yes | No (styled UI) | Yes | N/A |
| **Nuxt 4 + SSR** | Proven, tested | Works | Possible | Yes |
| **Bundle size** | ~50KB gzipped | ~80KB gzipped | ~22KB core | Parsing lib |
| **Learning curve** | Moderate | Shallow | Steep | Steep |
| **Maintenance** | Active 2026 | Active | Meta-backed | Unmaintained |
| **Use case fit** | Editor + preview | Quick WYSIWYG | Heavy editing | Just parsing |

**Why Tiptap best fits ParaSalvaraCuba:**
- **Native Vue 3 integration:** Feels natural; official Vue bindings (no community maintenance risk)
- **Markdown extension:** NEW in Tiptap 3.x; bidirectional (parse Markdown → edit → serialize back)
- **Headless architecture:** Customize UI to match design system without overriding component styles
- **Proven in Nuxt Studio:** Powers Nuxt's official content editor; battle-tested with SSR
- **Used at scale:** New York Times, The Guardian, Atlassian
- **2026 roadmap focus:** AI markdown generation, document conversion, enterprise features

**Comparison details:**

**md-editor-v3 (v6.4.1)** - Good standalone, bad for design system integration:
- Pros: Built-in toolbar, theme switching, Prettier integration
- Cons: Opinionated UI that doesn't match Nuxt UI; harder to customize; less flexible for Markdown serialization
- Use when: You want a complete editor UI out of box

**Lexical (Meta's editor)** - Overkill for civic platform:
- Pros: Excellent architecture; used in production at Meta
- Cons: No official Vue bindings (community packages not guaranteed); designed for complex documents; larger learning curve
- Use when: Building complex rich content with custom extensions

**markdown-it (parser only)** - Missing the editor:
- Pros: Lightweight; just parsing
- Cons: Requires custom editor UI; no editing experience; more work for same result
- Use when: Only rendering Markdown (not editing)

### Installation & Dependencies

```bash
npm install @tiptap/vue-3@^3.20.5 @tiptap/pm @tiptap/starter-kit @tiptap/extension-markdown
```

**Dependency tree:**
- `@tiptap/vue-3` - Vue 3 integration layer
- `@tiptap/pm` - ProseMirror (auto-installed as peer dependency)
- `@tiptap/starter-kit` - Common extensions (bold, italic, heading, list, blockquote, code, etc.)
- `@tiptap/extension-markdown` - Bidirectional Markdown support (NEW, early release)

**Version strategy:**
- Pin `@tiptap/vue-3@^3.20.5` to avoid breaking changes during v1.1 dev
- Upgrade together if needed (all Tiptap packages should match major.minor)

### Nuxt 4 Integration Pattern

**Critical for SSR:** Set `immediatelyRender: false` to prevent server-side rendering (Tiptap needs browser APIs).

**Example setup in component:**
```vue
<template>
  <div v-if="editor" class="markdown-editor">
    <EditorContent :editor="editor" />
  </div>
</template>

<script setup lang="ts">
import { useEditor, EditorContent } from '@tiptap/vue-3'
import StarterKit from '@tiptap/starter-kit'
import Markdown from '@tiptap/extension-markdown'

const editor = useEditor({
  extensions: [
    StarterKit,
    Markdown,
  ],
  content: props.initialMarkdown,
  immediatelyRender: false, // Critical for Nuxt 4 SSR
})

watch(editor, (newEditor) => {
  if (newEditor) {
    emit('update:markdown', newEditor.getMarkdown())
  }
})

onBeforeUnmount(() => {
  editor?.destroy()
})
</script>
```

## 2. Design System Integration

### CRITICAL CLARIFICATION: What is "Stitch"?

The brief mentions "Stitch design system" but three distinct products exist with that name:

#### Option A: Google Stitch (AI Design Tool)
[Google Stitch](https://stitch.withgoogle.com/) - Generative UI tool from Google Labs (launched March 2025, updated March 2026)

**Capabilities:**
- AI-powered UI design from text prompts or screenshots
- Exports production code in 7 frameworks (Vue.js included as of March 2026)
- DESIGN.md file captures design tokens for AI agents
- Multi-screen generation (up to 5 screens)
- Free tier available; Google account required

**Integration approach:**
```
Google Stitch (AI tool) → Generate UI designs → Export Vue components →
Hand-integrate into Nuxt → Customize for civics branding
```

**Pros:** Rapid design iteration; AI-assisted UX
**Cons:** External tool (not embedded in workflow); manual integration step; design system export may need tweaking

**Best for:** Rapid prototyping; design exploration

---

#### Option B: Stitches (CSS-in-JS Library)
[Stitches by Modulz](https://stitches.dev/) - CSS-in-JS styling library

**Features:**
- Near-zero runtime CSS-in-JS
- Works with any framework (Vue, React, Svelte)
- Variant system for component APIs
- Built-in theming and tokens

**Example:**
```javascript
import { styled } from '@stitches/react' // or Vue equivalent via @stitches/core
const Button = styled('button', {
  backgroundColor: '$primary',
  '&:hover': { opacity: 0.8 }
})
```

**Pros:** Lightweight CSS solution; type-safe variants
**Cons:** NOT recommended for Nuxt because Tailwind CSS v4 is already standard; duplicates styling approach

**Best for:** Custom component libraries; if not using Tailwind

---

#### Option C: Nuxt UI v4 (RECOMMENDED)
[Nuxt UI](https://ui.nuxt.com/) - Official Nuxt design system (free, open-source as of 2026)

**What it is:**
- 110+ pre-built components (button, card, modal, form, editor, etc.)
- Powered by Tailwind CSS v4 + Reka UI
- Official Nuxt project; built for Nuxt 4
- Semantic color system (7 colors, runtime customizable)
- Free Figma kit with 2,000+ variants

**Tailwind v4 (March 2026 release):**
- 5x faster full builds; 100x faster incremental builds
- New CSS features: cascade layers, @property, color-mix()
- Semantic variable system for theming

**Components relevant to ParaSalvaraCuba:**
- Form inputs (for idea/comment creation)
- Editor component (built on Tiptap!)
- Card/list components (for idea cards)
- Modal (for voting, comments)
- Badge/tag (for idea categories)
- Dropdown (for filtering)
- Button/link variants

**Pros:**
- Official Nuxt project; guaranteed compatibility
- 110+ components = less custom CSS to maintain
- Tailwind v4 = modern CSS, fast builds
- Editor component already uses Tiptap (direct compatibility)
- Runtime color customization (no rebuild needed for theme changes)

**Cons:**
- Learning Tailwind utility classes (minor; similar to Bootstrap)
- Component customization via `@apply` or inline classes (different from scoped CSS)

**Best for:** Complete design system; reducing custom CSS; consistent UI

## 3. Backend Considerations

### Markdown Storage Strategy

**Decision:** Store raw Markdown in PostgreSQL; parse/render on client

**Why client-side parsing:**
- Tiptap `@tiptap/extension-markdown` handles all parsing
- Markdown is semantic markup (not HTML); safe to store raw
- No server-side parsing libraries needed (simpler backend)
- Smaller deployment footprint
- Iteration on editor features decoupled from API

**Why NOT server-side parsing:**
- Would require `marked`, `markdown-it`, or `remark` on backend
- Adds complexity; extra dependencies in Node.js layer
- Slower API responses (markdown parsing per request)
- Changes to rendering logic require backend redeploy
- Database stores pre-rendered HTML (less future-proof)

### Database Schema Changes

**Currently:** Ideas have `description` (text), comments have `content` (text)

**v1.1 approach:** Add new columns for Markdown, keep old columns for backward compatibility

```sql
-- Existing ideas table - ADD Markdown support
ALTER TABLE ideas
ADD COLUMN IF NOT EXISTS description_markdown TEXT;

-- Existing comments table - ADD Markdown support
ALTER TABLE comments
ADD COLUMN IF NOT EXISTS content_markdown TEXT;

-- Migration: backfill if needed
UPDATE ideas SET description_markdown = description WHERE description_markdown IS NULL;
UPDATE comments SET content_markdown = content WHERE content_markdown IS NULL;

-- Future: once all v1.0 data migrated, can DROP old columns (v2.0+)
```

**Data model:**
- Column type: `TEXT` (PostgreSQL unlimited length for single value)
- Example Markdown value: `"# Bug Report\n\nThe voting system fails when...\n\n**Steps to reproduce:**\n1. Create idea\n2. Click vote button"`
- Parsing: Always on client via Tiptap
- Storage format: Raw Markdown string

**NO API changes needed:**
- Existing endpoints (`POST /api/ideas`, `POST /api/comments`) stay the same
- Frontend sends raw Markdown in `description` / `content` fields
- Backend stores as-is (no parsing logic)
- Client renders via Tiptap

### Content Validation

**Keep existing validation pattern (Vee-Validate + Yup in frontend):**

```typescript
// Already in your stack
const ideaSchema = yup.object({
  title: yup.string().min(5).max(200).required(),
  description: yup.string()
    .min(20, 'Description must be at least 20 characters')
    .max(10000, 'Description must be under 10,000 characters')
    .required(),
})
```

**No backend schema changes:**
- Zod validation on Express (from v1.0 STACK.md) works with Markdown strings
- Markdown is plain text; no special validation needed
- Length limits apply to raw Markdown (not rendered HTML)

### Performance Impact

**Negligible for v1.1 scale:**
- Markdown parsing happens in browser (client-side)
- Server only stores/retrieves text
- Database queries unchanged (just different column)
- No server CPU used for rendering

**If scale becomes issue (v1.2+):**
- Could cache rendered HTML in column
- But: defeats purpose of storing Markdown (loses future rendering flexibility)
- Better approach: implement caching layer (Redis) for popular ideas
