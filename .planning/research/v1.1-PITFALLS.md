# Pitfalls Research: v1.1 Markdown & Design System

**Project:** ParaSalvaraCuba IdeaHub
**Milestone:** v1.1 — Polish & Design
**Researched:** March 27, 2026
**Overall Confidence:** HIGH (verified against 2026 security advisories, design system reports, and regression testing best practices)

---

## Executive Summary

Adding Markdown editing, design system overhaul, and stability improvements to an active production platform creates three intersecting risk zones:

1. **Markdown Security (CRITICAL):** XSS vulnerabilities via unsanitized Markdown rendering are actively exploited in production systems (multiple 2026 CVEs documented). This is the highest-priority pitfall.

2. **Design System Drift (HIGH):** Partial component adoption without clear ownership leads to "design debt" where some UI uses new tokens and some doesn't, creating visual inconsistency and team confusion.

3. **Regression During Fixes (HIGH):** Voting system fixes or comment threading changes during active user engagement risk creating new bugs in dependent features. Race conditions in vote upserts require careful testing.

4. **Data Breaking Changes (MEDIUM):** Existing plaintext descriptions in database will render differently when parsed as Markdown. Requires wrapper/migration strategy.

This research document prevents those pitfalls with specific, actionable prevention strategies mapped to v1.1 phases.

---

## Critical Pitfalls

Mistakes that cause data corruption, security breaches, or require major rewrites.

### Pitfall 1: XSS via Unsanitized Markdown (CRITICAL RISK)

**What goes wrong:**
Users inject malicious JavaScript through Markdown syntax: `[click me](javascript:alert('xss'))` or raw HTML in Markdown. Without proper sanitization, this executes in other users' browsers, stealing session tokens or data.

**Real-world evidence (2026):**
- **CVE-2026-33500:** Stored XSS via Markdown JavaScript URIs in ParsedownSafeWithLinks (incomplete fix)
- **CVE-2026-33066:** SiYuan RCE via unsanitized Bazaar README rendering
- **CVE-2026-25516:** NiceGUI ui.markdown() XSS via innerHTML without sanitization
- Multiple platforms in 2026 suffered Markdown XSS because developers assumed libraries sanitize by default

**Why it happens:**
Developers assume Markdown renderers are secure by default. They're not. Most Markdown libraries:
- Allow raw HTML to pass through unchanged (unless sanitization is enabled)
- Process dangerous link types like `javascript:` without escaping
- Apply sanitization at parse-time instead of render-time (easier to bypass)

**Consequences:**
- Session hijacking (attackers steal authentication tokens stored in localStorage)
- Stored XSS (payload persists in database, affects all users viewing that idea/comment)
- Credential theft (malicious scripts capture typing in reply fields)
- Platform credibility collapse (civic platform with XSS is unusable and harmful)
- Government/partner loss of trust

**Prevention (Priority: CRITICAL):**

1. **Use DOMPurify for post-render sanitization** (MANDATORY)
   - After Markdown library renders HTML, pass result through DOMPurify before inserting into DOM
   - Correct flow: parse Markdown → DOMPurify → insert into DOM
   - Wrong flow: parse Markdown → insert into DOM (XSS vector open)
   - [DOMPurify GitHub](https://github.com/cure53/DOMPurify) is industry standard (verified in 2026 CVE disclosures)

   ```typescript
   // SAFE approach:
   import DOMPurify from 'dompurify'
   import { marked } from 'marked'

   function renderSafeMarkdown(content: string): string {
     const html = marked(content)
     const clean = DOMPurify.sanitize(html)
     return clean
   }
   ```

2. **Server-side sanitization is non-negotiable**
   - Sanitize on backend during API response, not frontend only
   - Store raw Markdown in database; sanitize during rendering on client
   - This way: if Markdown spec changes, old content auto-benefits from new rules
   - Frontend sanitization is defense-in-depth, but backend is primary

3. **Restrict link protocols in Markdown renderer**
   - Configure Markdown renderer to reject `javascript:`, `data:`, `vbscript:` protocols
   - Example (using `marked`):
     ```typescript
     marked.use({
       renderer: {
         link(token) {
           if (!token.href.match(/^https?:\/\//)) {
             return null // reject non-http links
           }
           return `<a href="${token.href}">${token.text}</a>`
         }
       }
     })
     ```

4. **Test with OWASP XSS payloads**
   - Create test cases for known XSS vectors:
     - `[xss](javascript:alert(1))`
     - `<img src=x onerror=alert(1)>`
     - `<script>alert(1)</script>`
     - `<svg/onload=alert(1)>`
     - `[harmless](javascript:void(0))`
   - Verify all render as escaped text, not executable code
   - Run XSS test suite in Phase 5 before any user-facing launch

5. **Configure DOMPurify with strict allowlist**
   ```typescript
   DOMPurify.setConfig({
     ALLOWED_TAGS: ['b', 'i', 'em', 'strong', 'a', 'p', 'br', 'ul', 'ol', 'li', 'h1', 'h2', 'h3', 'h4', 'h5', 'h6', 'blockquote', 'code', 'pre'],
     ALLOWED_ATTR: ['href', 'title'],
     KEEP_CONTENT: true,
     RETURN_DOM: false
   })
   ```

**Detection (Warning Signs):**
- Monitor for 401/403 errors on vote endpoints (sign of token theft)
- User reports of unexpected actions on their account
- Inspect network traffic: unusual API calls with no user interaction
- Test in browser: if script tags execute, sanitization failed
- Penetration testing: attempt injection via ideas, comments; verify blocked

**When to address:** **Phase 4 (Markdown Implementation)** — implement DOMPurify during initial Markdown feature build, not as afterthought

**Testing phase:** Phase 5 (Testing & Launch) — comprehensive XSS test suite must pass before any launch

### Pitfall 2: Breaking Change — Plaintext to Markdown Rendering (HIGH RISK)

**What goes wrong:**
Existing ideas/comments stored as plaintext: `"Check out [https://example.com](https://example.com) for details"`. When Markdown parser processes this, the text becomes a link, but the URL was just in the description text, not formatted as Markdown syntax. Result: ideas now display differently, confusing users.

More dangerous: plaintext with special characters like `*bold*` or `_italic_` now renders as formatted text, changing the meaning. An idea about "multiplying votes by 2*" would display as "multiplying votes by 2" with asterisk missing.

**Why it happens:**
v1.0 stored plain text. v1.1 adds Markdown parsing without migration strategy, assuming old data can be re-parsed as-is. Developers miss the breaking change assumption.

**Consequences:**
- User confusion ("I didn't format it that way")
- Visual inconsistency (old ideas look different from new ones)
- Ideas with code examples break (`*` for multiplication becomes italic marker)
- Ideas with math notation fail (`^2` in plaintext becomes superscript if renderer supports it)
- Support burden ("Why is my idea different?")
- Ideas become harder to read if special characters were intentional

**Prevention (Priority: HIGH):**

1. **Migrate plaintext to wrapped "plain text" Markdown**
   - Mark all pre-v1.1 ideas with a flag: `is_plaintext: true`
   - Render plaintext ideas as literal text (escape special chars), not Markdown
   - New ideas created after v1.1 launch: `is_plaintext: false` (parsed as Markdown)
   - This guarantees old ideas look identical to v1.0

   Schema change:
   ```sql
   ALTER TABLE ideas ADD COLUMN is_plaintext BOOLEAN DEFAULT true;
   ALTER TABLE comments ADD COLUMN is_plaintext BOOLEAN DEFAULT true;

   -- After v1.1 launch, set new content to false:
   UPDATE ideas SET is_plaintext = false WHERE created_at > '2026-03-27T00:00:00Z';
   UPDATE comments SET is_plaintext = false WHERE created_at > '2026-03-27T00:00:00Z';
   ```

2. **Two-phase rollout approach** (borrowed from Payload CMS migration pattern)
   - **Phase A (Preview):** Add `is_plaintext` flag; render old content as plaintext, new content as Markdown (user-facing, no data change)
   - **Phase B (Commit):** Once confident, run migration script to set flags permanently
   - If issues arise during Phase A, revert is trivial (just toggle flag back to true)
   - This is safer than "migrate everything at once"

3. **Test rendering for edge cases**
   - Ideas with URLs in plaintext (should stay as plain text, not become clickable links)
   - Ideas with code examples (`*asterisks*` should stay literal, not italic)
   - Ideas with math notation or special symbols
   - Ideas with leading/trailing whitespace
   - Run full regression test on existing 100+ ideas

4. **Provide user-facing explanation**
   - Launch notes: "v1.1 adds Markdown support for new ideas. Existing ideas remain unchanged."
   - This sets clear expectation: old ≠ new, and that's intentional
   - Users won't be confused if they see old idea in plaintext and new idea in Markdown

**Detection (Warning Signs):**
- Visual inspection: render sample of old ideas; verify they look identical to v1.0 screenshots
- Monitor idea creation: compare plaintext count to Markdown count; should change at launch
- User feedback: ask in first week "Do existing ideas look right?"

**When to address:** **Phase 2 (Data Preparation)** — add flag and migration script BEFORE Markdown rendering code lands

**Testing phase:** Phase 5 — regression test all existing ideas before launch; verify they're pixel-perfect identical to v1.0

### Pitfall 3: Race Condition in Vote Upsert During Concurrent Requests (HIGH RISK)

**What goes wrong:**
Current voting logic (v1.0):
1. Check if vote exists: `SELECT id FROM votes WHERE idea_id = $1 AND email = $2`
2. If exists: UPDATE; if not: INSERT

Under high concurrency, two simultaneous requests from the same user for the same idea can both see "no vote exists," then both INSERT, creating duplicate votes. This violates the assumption "one vote per user per idea" and inflates vote counts.

Current code comment: "Comment votes don't have a database constraint (NULL handling issue), so we handle it at app level" — this is precisely the race condition vector.

**Why it happens:**
Checking and inserting are two separate database operations. Between the SELECT and INSERT, another request can insert the same vote. The check-first logic won't catch it.

**Consequences:**
- Vote counts become invalid (user's single vote counts as 2 or more)
- Ranking algorithms break (ideas with inflated votes rank higher than they should)
- Users see confusing vote UI (they voted once, but count shows 2+)
- Edge case: rapid voting (up/down spam) could create 3-10 votes instead of 1
- Ideas appear more popular than they are (undermines civic credibility)

**Real-world evidence:**
[HackerOne blog on race condition voting](https://www.hackerone.com/blog/how-race-condition-vulnerability-could-cast-multiple-votes) documents how race conditions in voting systems allow attackers to artificially inflate vote counts.

**Prevention (Priority: HIGH):**

1. **Use database-level constraint + exception handling** (RECOMMENDED for v1.1)
   - Add UNIQUE constraint to votes table:
     ```sql
     ALTER TABLE votes ADD CONSTRAINT unique_idea_vote
       UNIQUE (idea_id, email, comment_id);
     ```
   - Change upsert logic to: try INSERT; if constraint violation, UPDATE
   - This guarantees atomicity at database level, eliminating race conditions

   ```typescript
   try {
     // Try to insert
     await query(
       'INSERT INTO votes (idea_id, email, comment_id, vote_value) VALUES ($1, $2, $3, $4)',
       [ideaId, userEmail, commentId, voteValue]
     )
   } catch (err) {
     // If constraint violation, update
     if (err.code === '23505') { // PostgreSQL unique violation
       await query(
         'UPDATE votes SET vote_value = $1, updated_at = NOW() WHERE idea_id = $2 AND email = $3 AND comment_id = $4',
         [voteValue, ideaId, userEmail, commentId]
       )
     } else throw err
   }
   ```

2. **OR use database upsert syntax** (PREFERRED for PostgreSQL)
   - Use `INSERT ... ON CONFLICT ... DO UPDATE` (PostgreSQL 9.5+, available in your stack)
   - This is atomic, even under concurrency:
     ```sql
     INSERT INTO votes (idea_id, email, comment_id, vote_value)
     VALUES ($1, $2, $3, $4)
     ON CONFLICT (idea_id, email, comment_id) DO UPDATE
     SET vote_value = $4, updated_at = NOW()
     ```
   - This is the cleanest solution for PostgreSQL

3. **Test with load testing**
   - Simulate 10 concurrent requests from same user voting on same idea
   - Verify vote count = 1, not 10
   - Measure query performance (upsert should be as fast or faster than separate queries)
   - Use Apache JMeter or Artillery for load test

4. **Verify no duplicates currently exist**
   - Query to find duplicates:
     ```sql
     SELECT idea_id, email, comment_id, COUNT(*) as count
     FROM votes
     GROUP BY idea_id, email, comment_id
     HAVING COUNT(*) > 1
     ```
   - If any rows appear, race condition has already occurred
   - Document before-state for legal/audit purposes

**Detection (Warning Signs):**
- Query finds duplicates in votes table (see above)
- Vote count on popular ideas jumps unexpectedly
- Same user appears multiple times for single idea in votes table
- Load testing shows vote count increases beyond expected users

**When to address:** **Phase 3 (Voting Stability)** — fix race condition BEFORE design system rollout

**Testing phase:** Phase 5 — load tests must include concurrent vote scenarios; verify constraint prevents duplicates

## Moderate Pitfalls

Mistakes that cause delays, visual regressions, or technical debt.

### Pitfall 4: Design System Drift (Partial Component Adoption)

**What goes wrong:**
Design system (Stitch) introduces new tokens (colors, spacing, typography). Some components updated to use tokens; others still use hardcoded colors. Result:
- Button on home page uses Stitch tokens (correct color)
- Same button in comment thread uses old hardcoded color (incorrect)
- Users see color inconsistency
- Team confusion: "Which button is the source of truth?"

**Why it happens:**
Design system rollout is announced. Teams start converting components but don't finish. Halfway through, pressure shifts to bug fixes or other features. Old and new components coexist indefinitely.

Real 2026 design system report: "Design drift is a silent killer. Teams move at different speeds, tokens get duplicated, engineers override styles to hit deadlines, resulting in inconsistent shades of blue, competing button sizes, and multiple naming conventions."

**Consequences:**
- Visual inconsistency across UI (undermines design credibility)
- Increased technical debt (two versions of truth for every component)
- Slow adoption (teams don't trust system if it's incomplete)
- Maintenance nightmare (fixes must be applied in two places)
- Time wasted: designers maintain Stitch kit, engineers maintain hardcoded values separately

**Prevention (Priority: HIGH):**

1. **Define clear scope: which components, in which order**
   - Phase 4a: Basic components (Button, Input, Link) — 5 components
   - Phase 4b: Layout components (Card, Container) — 3 components
   - Phase 4c: Data display (IdeaCard, CommentThread, VoteButton) — 3 components
   - Don't attempt full rollout at once
   - Document completion status per component in README

   Example tracking:
   ```
   ## Stitch Adoption Progress
   - [x] Button — v1.1.0
   - [x] Input — v1.1.0
   - [x] Link — v1.1.0
   - [ ] Card — v1.1.1
   - [ ] IdeaCard — v1.1.1
   - [ ] CommentThread — v1.1.2
   ```

2. **Use feature flags for incremental rollout**
   - New Stitch version behind feature flag: `useStitchComponents: true/false`
   - By default: false (keep old components until migration complete)
   - Gradually: true (enable for specific pages/routes)
   - All-at-once conversion is risky; percentage-based rollout catches issues early

   ```typescript
   // In component:
   const useStitch = featureFlags.enableStitch // toggleable
   const ComponentToUse = useStitch ? StitchButton : LegacyButton
   ```

3. **Establish clear ownership and timeline**
   - One person owns Stitch migration (not "everyone when they have time")
   - Publish migration roadmap with dates: "Buttons done March 31, Cards April 7"
   - Block component updates in old system once migration starts
   - PR requirement: "If you touch a design element, update to use Stitch tokens"

4. **Measure adoption progress**
   - Calculate: (Components using tokens) / (Total components) = % adoption
   - Target: 100% before v1.1 launch, not "eventually"
   - Weekly checkin: "90% adoption" is a concrete milestone
   - If adoption stalls, design system isn't trusted; investigate why

5. **Test all pages with Stitch components before launch**
   - Visual regression: compare old vs. new screenshots
   - All pages should look identical or better, never worse
   - Verify consistency across pages (same button looks same everywhere)

**Detection (Warning Signs):**
- Visual inspection: load two different pages; colors don't match → drift occurred
- Code inspection: grep for hardcoded color values in newly-designed components
- During PR review: if a component changed but doesn't use tokens, flag it
- Adoption metrics: % of components using tokens stays flat for 2+ weeks

**When to address:** **Phase 4 (Design System Rollout)** — scope components BEFORE writing code; establish ownership

### Pitfall 5: Dark Mode Regression with New Color Tokens

**What goes wrong:**
Stitch design system introduces new color tokens based on light mode palette. Tokens roll out; dark mode users report:
- Text is hard to read (contrast too low)
- Links disappear (token color is dark on dark background)
- Accent colors look neon/saturated (brand colors not adjusted for dark mode)

This happens because brand colors that work on light backgrounds are too saturated or too dark for dark mode.

**Why it happens:**
Color tokens designed without testing both light and dark themes. Developer assumes "if it looks good on light, dark mode will invert it automatically" — but design system tokens don't invert automatically. Each theme needs explicit color definitions.

**Consequences:**
- Dark mode becomes unusable (accessibility regression)
- Users with accessibility needs (eye strain, photophobia) lose usability
- Civic engagement platform becomes inaccessible to portion of user base
- Platform credibility hit ("They broke dark mode")
- Legal accessibility liability (WCAG AA compliance violation)

**Prevention (Priority: HIGH):**

1. **Design tokens for BOTH light and dark explicitly**
   - Don't design once and assume inversion
   - Create light tokens AND dark tokens for each semantic color:
     ```typescript
     // GOOD:
     const colors = {
       light: {
         primary: '#1e3a5f',      // dark blue on light bg
         background: '#ffffff',
         text: '#000000'
       },
       dark: {
         primary: '#5ba3d0',      // lighter blue on dark bg
         background: '#0f1419',
         text: '#ffffff'
       }
     }

     // BAD:
     const colors = { primary: '#1e3a5f' } // one value, fails in dark mode
     ```

2. **Test with real users before launch**
   - Have dark mode users review designs in actual dark mode (not screenshot)
   - Use tools: measure WCAG contrast ratios for dark mode (should be >= 4.5:1 for body text, 3:1 for large text)
   - Test on real devices: dark mode on phone, laptop, external monitor
   - 2026 design standard: "It is impossible to indicate that dark mode is fully designed without thorough testing"

3. **Use semantic tokens, not color tokens**
   - Instead of: "button-color-blue"
   - Use: "button-primary", "button-secondary"
   - Each theme assigns its own color to semantic tokens
   - This way: dark mode can map "button-primary" to lighter blue; light mode to darker blue

   ```typescript
   // GOOD: semantic tokens
   const button = {
     primary: colors[currentTheme].primaryButton,
     secondary: colors[currentTheme].secondaryButton
   }

   // BAD: color-only tokens
   const button = {
     blue: '#1e3a5f', // too dark for dark mode
     lightBlue: '#5ba3d0'
   }
   ```

4. **Audit existing dark mode functionality**
   - Before Stitch rollout, verify current dark mode works
   - Document contrast ratios (text on background, links on text, etc.)
   - New tokens must meet or exceed existing contrast levels
   - Don't regress accessibility that's already working

5. **Use browser devtools to test**
   - Chrome DevTools: "Inspect → Rendering → Emulate CSS media feature prefers-color-scheme: dark"
   - Firefox: "Inspect → Inspector → Compatibility panel → Check dark color issues"
   - WCAG Contrast Checker extension: verify all text meets 4.5:1 ratio

**Detection (Warning Signs):**
- Dark mode user reports: "Text is hard to read"
- Visual inspection: toggle dark mode; text disappears or looks neon
- Accessibility audit: contrast ratio < 4.5:1 for body text
- Browser extension flags: low contrast issues

**When to address:** **Phase 4 (Design System Rollout)** — test dark mode BEFORE rolling out tokens; fix before launch

### Pitfall 6: Breaking Vote Functionality When Fixing Race Condition

**What goes wrong:**
Phase 3 fixes the race condition in voting (Pitfall 3) by adding UNIQUE constraint. But the constraint is applied AFTER data already contains duplicates from v1.0.

Adding constraint fails: "Cannot add UNIQUE constraint; duplicate values exist."

Developer resolves by deleting some duplicate votes. But which vote to keep? If they delete the most recent vote from a user, it looks like the user unvoted. If they delete randomly, it's arbitrary.

Result: vote counts change during the fix, and users see their votes disappear during v1.1 testing/launch.

**Why it happens:**
Fixing data integrity requires both schema change AND data cleanup. Developers focus on schema (adding constraint) but skip data preparation (removing duplicates first).

**Consequences:**
- Vote count changes unexpectedly during v1.1
- Users see their vote disappear (unvoting without requesting it)
- Idea rankings shift (some votes deleted, others retained)
- User confusion: "Did my vote disappear or did theirs go up?"
- Loss of trust: "Platform lost my vote data"

**Prevention (Priority: HIGH):**

1. **Apply constraint in two phases: prepare first, then enforce**
   - **Phase A:** Identify and remove duplicates from old data BEFORE schema change
     ```sql
     -- Keep the most recent vote per user per idea; delete older duplicates
     DELETE FROM votes v1
     WHERE id NOT IN (
       SELECT DISTINCT ON (idea_id, email, comment_id) id
       FROM votes
       ORDER BY idea_id, email, comment_id, created_at DESC
     );
     ```
   - **Phase B:** Once duplicates removed, add constraint
     ```sql
     ALTER TABLE votes ADD CONSTRAINT unique_idea_vote
       UNIQUE (idea_id, email, comment_id);
     ```
   - This ensures constraint addition succeeds without data loss

2. **Test constraint addition against production data backup**
   - Export production database; apply constraint locally
   - If it fails, you'll know the exact duplicates before attempting in production
   - If it succeeds, you know exactly which cleanup will work
   - This is the safe approach: test on copy first

3. **Document what happened**
   - Record how many duplicates existed
   - Record how many votes were deleted during cleanup
   - Keep audit trail: "Cleaned up X duplicate votes on DATE at TIME"
   - This helps with any user questions later

4. **Communicate change to users (if noticeable)**
   - If vote counts change visibly, users notice
   - Launch notes: "v1.1 includes voting system fixes. Vote counts may adjust as we correct historical issues. Your current votes remain intact."
   - This sets expectation and prevents confusion

5. **Verify no data is lost**
   - Before cleanup: `SELECT COUNT(*) FROM votes` → record count
   - After cleanup: query same, verify count decreased only by duplicates
   - New votes (created after fix) should still be present
   - Total votes = original - duplicates

**Detection (Warning Signs):**
- Vote counts on high-traffic ideas change unexpectedly
- Counts drop > 10% during v1.1 launch
- Users report "my vote disappeared"
- Constraint addition fails with "duplicate values" error

**When to address:** **Phase 3 (Voting Stability)** — prepare data BEFORE applying constraint; don't apply constraint then cleanup

### Pitfall 7: Markdown Library Dependency Bloat

**What goes wrong:**
Team chooses a Markdown library (e.g., `marked`, `remark`, `markdown-it`). Library is fine initially, but:
- Library adds features you don't need (syntax highlighting, table parsing, footnotes)
- Bundle size grows (affects page load time)
- Library has security vulnerabilities (must update frequently)
- Library API changes (new version breaks compatibility)

Result: maintaining a heavier, more complex dependency than needed for simple Markdown.

**Why it happens:**
Developers choose popular, feature-rich libraries without evaluating necessity. "Marked is popular, let's use it" leads to including features never used.

**Consequences:**
- Larger bundle size (slower page load, more bandwidth)
- More security surface area (library vulnerabilities affect you)
- Maintenance burden (library updates might break things)
- Complexity overhead (unused features clutter API)

**Prevention (Priority: MEDIUM):**

1. **Choose minimal Markdown library for your scope**
   - IdeaHub needs: basic formatting (bold, italic, headers, lists, links) only
   - IdeaHub does NOT need: syntax highlighting, tables, footnotes, math
   - Minimal libraries: `micromark`, `markdown-it` (in minimal config)
   - Compare bundle size: use `npm bundle-phobia [package]`
   - For IdeaHub: aim for < 10KB library (gzipped)

   ```bash
   # Check sizes
   npm bundle-phobia marked           # ~20KB gzipped
   npm bundle-phobia markdown-it      # ~15KB gzipped
   npm bundle-phobia micromark        # ~8KB gzipped
   ```

2. **Pair with DOMPurify (separate, minimal library)**
   - Markdown renderer + DOMPurify is clean separation
   - Library choice: focus on correctness, not features
   - DOMPurify is small, single-purpose, well-maintained

3. **Pin library version in lock file**
   - Don't use `^3.0.0` (allows minor/patch updates)
   - Use `3.0.5` (exact version; update only when vetted)
   - Review changelog before updating
   - Small updates can introduce breaking changes

4. **Evaluate: can you use plain HTML + CSS instead?**
   - If ideas are short, simple formatting only: maybe plain HTML is sufficient
   - Markdown is powerful but adds complexity
   - For v1.1: start with Markdown, evaluate later if it's necessary
   - No shame in removing Markdown in v1.2 if simpler approach works

**Detection (Warning Signs):**
- Bundle size increases unexpectedly after adding Markdown library
- npm audit reports vulnerabilities in Markdown library
- Library updates break your code
- You use only 10% of library features

**When to address:** **Phase 4 (Markdown Implementation)** — library selection before any code written

## Minor Pitfalls

Mistakes that cause annoyance or technical debt but are fixable.

### Pitfall 8: Markdown Rendering in Plaintext Contexts

**What goes wrong:**
Developer renders Markdown in a place designed for plaintext:
- User email field shown in idea metadata: if email contains Markdown-like syntax (rare but possible), renders wrongly
- Comment author name: if author is "Jo*Smith" (with asterisk), renders as "Jo_Smith_" (italics)
- Timestamps or IDs: special characters get interpreted as Markdown

**Why it happens:**
Over-applying Markdown rendering without thinking about context. "All user content should be Markdown" is wrong; some fields are metadata, not rich content.

**Consequences:**
- Visual weirdness (user name italicized unexpectedly)
- Rendering bugs (email becomes mangled)
- Confusion ("I didn't format that")

**Prevention (Priority: LOW):**

1. **Be explicit about which fields are Markdown**
   - Markdown: idea.description, comment.body (only these two)
   - Plain text: idea.email, comment.email, user names, timestamps, IDs
   - Document this clearly in code comments

   ```typescript
   // Markdown fields (parse & sanitize)
   <div class="idea-body">{{ renderMarkdown(idea.description) }}</div>

   // Plaintext fields (escape HTML only)
   <p class="idea-meta">by {{ escapeHtml(idea.email) }} · {{ formatDate(idea.created_at) }}</p>
   ```

2. **Use separate rendering functions**
   - `renderMarkdown()` - parse Markdown, sanitize HTML
   - `escapeHtml()` - only escape HTML, no Markdown parsing
   - Use right function for each context

3. **Test with user data containing special characters**
   - Test email with `+` sign: `user+test@example.com`
   - Test name with asterisk: `Jo*Smith`
   - Test timestamp with underscores
   - Verify they render as plain text, not Markdown

**Detection (Warning Signs):**
- User name contains special characters and looks formatted
- Email addresses appear broken
- Plaintext fields have unwanted italics/bold

**When to address:** **Phase 4 (Markdown Implementation)** — establish rendering rules BEFORE implementation

### Pitfall 9: Testing Regressions When Fixing Comment Threading

**What goes wrong:**
Existing comment threading works. v1.1 fixes an edge case (e.g., comments older than 30 days). Change to the comment query logic inadvertently breaks:
- Nested reply rendering (indentation wrong)
- Vote counts on old comments (query didn't account for comment_id)
- Comment sorting (oldest-first now shows newest-first)

Result: comments that worked before now look broken, but only for specific conditions.

**Why it happens:**
Changing comment query or rendering logic affects dependent features. Without regression tests, these breaks only surface after deployment.

**Consequences:**
- Users see broken comment threads during v1.1 testing
- Takes time to debug (issue is in query, not component)
- Requires hotfix/rollback, delaying launch
- Loss of confidence in testing rigor

**Prevention (Priority: MEDIUM):**

1. **Write regression test suite for comments BEFORE any changes**
   - Test cases: single comment, nested 3 levels deep, 100 comments on one idea, comments older than 30 days, comments with votes
   - Each test verifies: rendering correct, votes counted right, sorting correct
   - Use snapshot testing (Jest/Vitest) to catch visual changes

   ```typescript
   test('Comments render correctly when nested 3 levels deep', () => {
     const comments = createTestComments({ depth: 3 })
     const rendered = renderCommentThread(comments)
     expect(rendered).toMatchSnapshot()
   })

   test('Vote count is correct on old comments', () => {
     const oldComment = createComment({ createdAt: 30 days ago })
     const votes = queryVotesForComment(oldComment.id)
     expect(votes.length).toBe(5) // expected count
   })
   ```

2. **Create test database with realistic data**
   - 1000 ideas, 5000 comments, 20000 votes
   - Seed data with edge cases: old comments, many nested replies, high-voted comments
   - Run queries against this data to identify performance/correctness issues

3. **Test before and after each fix**
   - Before: run test suite, capture results
   - After: run test suite, verify no new failures
   - Use `vitest run` before committing

4. **Use query explain plan to verify efficiency**
   - When changing comment queries, check execution time
   - Run `EXPLAIN ANALYZE` on old and new queries
   - If new query is 10x slower, reconsider approach

**Detection (Warning Signs):**
- Visual regression: comment thread looks different after fix
- Performance regression: page load slow after fix
- Functional regression: votes don't count right after fix

**When to address:** **Phase 3 (Voting Stability)** — write test suite BEFORE any changes to voting/comments

### Pitfall 10: Incomplete Stitch Token Documentation for Developers

**What goes wrong:**
Design system introduces tokens. Designer creates Figma kit with all colors, spacing, etc. But developers don't know:
- How to use tokens in code
- Where token values are defined
- How to add new components using tokens
- What to do if their component doesn't fit existing token

Result: developers ignore tokens and hardcode values. Design system becomes "design-only" artifact, not developer-usable.

**Why it happens:**
Design system created by designers; developer documentation is afterthought. Developers aren't trained on how to use tokens.

**Consequences:**
- Tokens unused by most developers
- Design inconsistency (hardcoded values don't match tokens)
- Maintenance burden (designers maintain Figma; developers maintain code separately)

**Prevention (Priority: MEDIUM):**

1. **Create developer-focused documentation**
   - Include: code examples for every component using tokens
   - Show: how to import tokens, how to apply them, common patterns
   - Example:
     ```typescript
     import { colors, spacing } from '@/design-tokens'

     const buttonStyle = `
       background: ${colors.primary};
       padding: ${spacing.md};
       color: ${colors.text};
     `
     ```

2. **Provide token file in code (not just Figma)**
   - Don't just show Figma; include actual token file developers can use
   - Generate tokens from Figma automatically (tools: Supernova, Zeroheight)
   - Developers access tokens directly in code:
     ```typescript
     import { colors, spacing, typography } from '@design-system/tokens'
     ```

3. **Train developers with workshop before rollout**
   - 30-min walkthrough: "Here's a token, here's how to use it, let's convert one component together"
   - Hands-on: developer converts one component as training
   - Q&A: address confusion before it becomes habit

4. **Create "add new component to Stitch" checklist**
   - When team needs new component: follow checklist
   - Checklist includes: use tokens, test light/dark, document in design kit
   - Block components that don't follow checklist from being merged

**Detection (Warning Signs):**
- Code review: new components use hardcoded colors instead of tokens
- grep for hardcoded values: should be near-zero after rollout
- Developer feedback: "I don't know how to use the tokens"

**When to address:** **Phase 4 (Design System Rollout)** — documentation before launch
