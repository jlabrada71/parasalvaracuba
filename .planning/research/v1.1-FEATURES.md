# Features Research: v1.1 — Markdown Editing & Design System

**Project:** ParaSalvaraCuba v1.1
**Researched:** 2026-03-27
**Overall Confidence:** MEDIUM (Markdown requires implementation choices; Stitch clarification needed)

---

## Executive Summary

ParaSalvaraCuba v1.0 delivered core civic engagement features (ideas, voting, threaded comments). v1.1 builds on this by adding **Markdown support for content richness** and **design system standardization for visual cohesion**. Both additions are cosmetic/quality improvements to existing features rather than new functionality—they enhance ideas and comments that users have already contributed.

**Key research finding:** The project should use **Marked.js + DOMPurify** for Markdown rendering (proven performance + security), **Shopify Polaris** or a lightweight custom design system for tokens (not "Stitch," which is a Google AI design tool), and focus v1.1 bug fixes on **voting uniqueness edge cases** (already partially fixed) and **mobile form responsiveness**.

---

## Markdown Editing

### What Users Expect

For civic engagement platforms, Markdown is a **differentiator, not table stakes**. Research shows:

- Users on platforms like Decidim and Consul expect **basic formatting**: bold, italics, links, bullet lists
- **Live preview is nice-to-have, not required** — Most civic proposals are edited once; users don't need real-time feedback
- **Raw Markdown editing (no toolbar) is acceptable** — Users familiar with Markdown expect it; others learn quickly
- **Security trumps features** — Platforms embedding Markdown without sanitization get hacked. Sanitization is mandatory.

**Competitive context:**
- Decidim: Supports rich formatting via Markdown; no visible toolbar
- Consul: Similar—Markdown input, rendered output, no WYSIWYG
- ChangeMakers: Simple text only (no formatting)

### Table Stakes for v1.1

#### 1. **Markdown rendering with sanitization (mandatory)**
- **Why:** User-generated content (ideas, comments) MUST be sanitized to prevent XSS attacks
- **Implementation:** Use **Marked.js** to parse Markdown → HTML, then **DOMPurify** to strip malicious tags
- **Complexity:** Low (two libraries, ~50 lines of integration code)
- **Notes:**
  - Recent XSS vulnerability (CVE-2025-24981) in markdown libraries highlights importance of sanitization
  - Best practice: Sanitize on **server-side after rendering**, not client-side
  - If using Nuxt, leverage existing utilities or add to server middleware

#### 2. **Support for common formatting: bold, italics, links, lists**
- **Why:** Core writing patterns for proposals and discussion
- **Implementation:** Marked.js handles this automatically (CommonMark compatible)
- **Complexity:** Zero—no additional code needed
- **Notes:** Users write Markdown naturally; rendering "just works"

#### 3. **Plaintext fallback for ideas/comments without Markdown**
- **Why:** Existing ideas and comments are plaintext; must display correctly
- **Implementation:** Treat plaintext as valid Markdown (Marked handles escaping)
- **Complexity:** Zero—backward compatible by design
- **Notes:** No migration needed; old content displays as plaintext, new content as formatted

#### 4. **Prevent rendering of malicious HTML/JavaScript**
- **Why:** Users might paste `<script>` tags or embed malicious links
- **Implementation:** DOMPurify whitelist approach—allow formatting tags, block scripts
- **Complexity:** Low (DOMPurify handles via config, ~20 lines)
- **Examples of what to block:**
  - `<script>alert('XSS')</script>` ❌
  - `<img src=x onerror="alert('XSS')">` ❌
  - `<a href="javascript:void(0)">` ❌
- **Examples of what to allow:**
  - `**bold text**` → `<strong>bold text</strong>` ✓
  - `[link](https://example.com)` → `<a href="https://example.com">link</a>` ✓
  - `- bullet item` → `<li>bullet item</li>` ✓

### Differentiators (Nice-to-Have for v1.1)

#### 1. **Live preview mode (side-by-side Markdown + rendered output)**
- **Value:** Better authoring experience; users see changes instantly
- **Complexity:** Medium (requires split-pane UI component)
- **Recommendation:** Defer to v1.2 if time allows, but not critical for launch
- **How:**
  - Left pane: Textarea with Markdown input
  - Right pane: Live-rendered preview using Marked + DOMPurify
  - Implementation: Use Vue 3 two-way binding; update preview on input

#### 2. **Markdown help tooltip or cheat sheet**
- **Value:** Users unfamiliar with Markdown can learn syntax
- **Complexity:** Low (static HTML popover)
- **Recommendation:** Worth adding if space allows
- **Implementation:**
  ```
  ? icon → Popover showing:
  **bold**, *italic*, [link](url), - list, > quote, `code`
  ```

#### 3. **Syntax highlighting in preview**
- **Value:** Code blocks stand out; improves readability
- **Complexity:** Medium (requires highlight.js or similar)
- **Recommendation:** Defer to v1.2
- **When:** Only if users share code examples frequently

### Anti-Features (Don't Build These)

#### 1. **WYSIWYG Editor (rich text editor with toolbar)**
- **Why it's bad:**
  - Adds bloat (TipTap, Slate, or similar = 100+ KB)
  - Users either know Markdown or don't—toolbar doesn't help much
  - Civic platforms favor simplicity over polish
  - Maintenance burden for little value
- **Alternative:** Raw Markdown with optional help tooltip
- **Confidence:** HIGH—civic platforms intentionally avoid WYSIWYG

#### 2. **Full HTML support (allow arbitrary HTML tags)**
- **Why it's bad:**
  - Opens XSS attack surface dramatically
  - Users can inject iframes, scripts, tracking pixels
  - Increases moderation burden (malicious/spam posts harder to detect)
  - Most civic platforms explicitly forbid HTML
- **Alternative:** Markdown + DOMPurify (safe subset of formatting)
- **Confidence:** HIGH—security requirement

#### 3. **Markdown table support**
- **Why it's bad:**
  - Civic proposals rarely need complex data tables
  - Table Markdown syntax is verbose and error-prone
  - If users need data, they should attach a spreadsheet (v1.2 file uploads)
- **Alternative:** Bullet lists or basic paragraph formatting
- **Confidence:** MEDIUM—may be requested but not essential

#### 4. **Custom emoji or shortcodes (:smile:)**
- **Why it's bad:**
  - Adds complexity (emoji parser library)
  - Civic context is serious (governance); emoji trivializes
  - Potential for inappropriate use (spam, mocking)
- **Alternative:** Keep text-only; let users use Unicode directly if desired
- **Confidence:** MEDIUM—low priority but low cost

## Design System Integration (Stitch vs. Design Tokens)

### Clarification: "Stitch" is Not a Design System Library

**Research finding:** The v1.1 goals mention "Stitch design improvements," but **Stitch** refers to Google's AI-powered UI design tool (launched 2026), not a reusable design system component library.

**Options for design system approach:**

#### Option A: Use Shopify Polaris (Recommended)
- **What it is:** Open-source design system with 60+ production-ready components, design tokens, and accessibility baked in
- **Components:** Buttons, forms, cards, modals, navigation, data tables, etc.
- **Accessibility:** Every component meets WCAG 2.1 AA (keyboard navigation, screen readers, focus management)
- **Design tokens:** Color, typography, spacing, shadows pre-defined
- **Installation:** `npm install @shopify/polaris`
- **When to use:** If you want consistent, accessible UI without building from scratch
- **Cost:** Free (MIT license)
- **Drawbacks:** Opinionated design (Shopify aesthetic); may feel heavy-handed for civic platform
- **Confidence:** HIGH—Polaris is production-grade and well-documented

#### Option B: Custom Design Token System (Lightweight)
- **What it is:** Define core design values (colors, typography, spacing) in CSS variables; use across components
- **Design tokens to define:**
  - **Colors:** Primary, secondary, neutral, accent, semantic (error, success, warning)
  - **Typography:** Font sizes (xs, sm, base, lg, xl), line heights, font weights
  - **Spacing:** Base unit (4px or 8px), then multiply (4px, 8px, 12px, 16px, 24px, 32px)
  - **Shadows, borders, radii:** Consistent visual depth
- **Implementation:** CSS variables or Tailwind config
- **When to use:** If you want design consistency without external dependencies
- **Cost:** Free (no libraries required)
- **Drawbacks:** Must build components yourself (more work than Polaris)
- **Confidence:** HIGH—this is standard practice in 2026 web development

#### Option C: Hybrid (Recommended for v1.1)
- **Approach:** Use design tokens (Option B) without committing to Polaris
- **Rationale:**
  - v1.0 components (ideas, comments, voting) are simple and already functional
  - Adding Polaris now would require refactoring existing components
  - Design tokens alone provide consistency without refactor work
  - Can adopt Polaris components incrementally in v1.2 if needed
- **Effort:** Low (1-2 days to define tokens, apply to existing components)
- **Payoff:** Visual cohesion, faster iteration, foundation for scaling

### Table Stakes for v1.1

#### 1. **Design token definitions (colors, typography, spacing)**
- **What to define:**
  - **Color palette:** Brand primary, secondary, neutral grays, semantic colors (error red, success green)
  - **Typography:** 1 or 2 typefaces (sans-serif recommended for web); sizes (12px, 14px, 16px, 18px, 20px, 24px)
  - **Spacing scale:** 4px base unit; multiples (4, 8, 12, 16, 24, 32, 48px)
  - **Borders & shadows:** Consistent depth (e.g., 0.5px gray border, subtle shadow)
- **Implementation:** CSS variables or Tailwind config
- **Complexity:** Low (1-2 hours to define)
- **Example:**
  ```css
  :root {
    --color-primary: #0066cc;
    --color-secondary: #00aa44;
    --color-neutral-50: #f9f9f9;
    --color-neutral-900: #111111;

    --font-base: 16px;
    --font-lg: 20px;
    --font-sm: 14px;

    --spacing-1: 4px;
    --spacing-2: 8px;
    --spacing-3: 12px;
    --spacing-4: 16px;
  }
  ```
- **Recommendation:** Add to `app/assets/css/design-tokens.css`; import globally in Nuxt config

#### 2. **Visual consistency across existing components**
- **What to apply:**
  - Idea cards: Use token colors (background), spacing (padding), typography (font sizes)
  - Comment items: Consistent spacing, borders, text colors
  - Vote buttons: Consistent colors (primary for upvote, secondary for downvote)
  - Forms (comment input, idea creation): Token-driven styling
- **Complexity:** Low to Medium (apply tokens to existing CSS)
- **No new components required** — Just refactor existing ones to use tokens

#### 3. **Accessibility baseline (WCAG 2.1 AA for new features)**
- **What's required:**
  - **Color contrast:** Text must have 4.5:1 contrast ratio (body text), 3:1 for large text
  - **Focus indicators:** Keyboard users can see focused elements (outline or highlight)
  - **Button sizing:** Tap targets ≥ 44x44px (mobile friendly)
  - **Form labels:** Associated with inputs (not floating labels that disappear)
  - **Semantic HTML:** Use `<button>`, `<label>`, `<input>` correctly (not divs as buttons)
- **Testing:** Use axe DevTools or WAVE browser extensions
- **Complexity:** Low if building correctly from start; High if retrofitting
- **For v1.1:** Focus on Markdown editor input (label visibility, tap targets) and comment form

### Differentiators (Nice-to-Have for v1.1)

#### 1. **Dark mode support**
- **Value:** Users prefer dark UI; improves accessibility for some
- **Complexity:** Medium (requires theme switcher + color scheme CSS)
- **Recommendation:** Defer to v1.2 if time allows
- **How:** CSS variables or Tailwind dark: mode
- **Confidence:** LOW—nice but not essential for civic platform

#### 2. **Responsive design tokens (different spacing on mobile vs desktop)**
- **Value:** Better use of screen space on mobile
- **Complexity:** Medium (requires breakpoint-aware CSS)
- **Recommendation:** Include in v1.1 if refactoring for tokens
- **Example:**
  ```css
  --spacing-4: 16px; /* desktop */
  @media (max-width: 640px) {
    --spacing-4: 12px; /* mobile */
  }
  ```
- **Confidence:** MEDIUM—important for mobile experience

#### 3. **Component storybook or documentation**
- **Value:** Design consistency reference; faster development
- **Complexity:** Medium (requires Storybook setup)
- **Recommendation:** Defer to v1.2
- **When:** After components stabilize

### Anti-Features (Don't Build These)

#### 1. **Full Shopify Polaris refactor in v1.1**
- **Why it's bad:**
  - v1.0 components already exist and work
  - Refactoring for Polaris is weeks of work for cosmetic gain
  - Risk: Breaking existing features mid-adoption
- **Alternative:** Design tokens (Option B above) + selective Polaris adoption in v1.2
- **Confidence:** HIGH—premature refactor is waste

#### 2. **Custom component library from scratch**
- **Why it's bad:**
  - Reinventing buttons, forms, modals = wasted effort
  - Security and accessibility gaps likely
  - Maintenance burden for features Polaris already provides
- **Alternative:** Polaris (Option A) or minimal custom system (Option B)
- **Confidence:** HIGH—not invented here trap

#### 3. **AI-generated UI (Google Stitch)**
- **Why it's bad:**
  - Stitch is a design tool, not a runtime component library
  - "AI-generated design" is unproven for civic platforms
  - Accessibility guarantees unclear
  - Governance platforms need human-reviewed UX, not algorithmic layouts
- **Alternative:** Human-designed tokens + Polaris or custom components
- **Confidence:** HIGH—AI design tools are experimental; stick to proven approaches

## Bug Fixes & Stability

### Known Issues from v1.0 (Already Fixed or Partially Fixed)

Based on git history analysis, ParaSalvaraCuba v1.0 → v1.1 transition had **voting uniqueness bugs** that have been addressed:

#### Issue 1: Duplicate vote prevention (FIXED)
- **What went wrong:** Users could vote multiple times on same idea/comment
- **Root cause:** Database constraint design (`UNIQUE (idea_id, email)`) didn't account for comment voting
- **How it was fixed:**
  - Simplified to app-level uniqueness (no database constraint)
  - API checks for existing vote before insert/update
  - Uses upsert pattern (INSERT ON CONFLICT)
- **Impact:** v1.0 already shipping with fix; no v1.1 work needed
- **Confidence:** HIGH—commits show thorough resolution

#### Issue 2: Comment vote field misalignment (FIXED)
- **What went wrong:** Comments had `body` field; API expected `content`
- **Root cause:** Schema mismatch between database and API
- **How it was fixed:** Standardized on `content` field across codebase
- **Impact:** Tests now pass; no v1.1 work needed
- **Confidence:** HIGH—git history confirms resolution

### Common Bugs to Watch For in v1.1

#### 1. **Mobile form input accessibility**
- **Common issue:** Text input fields too small (< 44px tap target), labels disappear on focus
- **Why it happens:** Mobile-first design often forgotten until late in cycle
- **Prevention for v1.1:**
  - Markdown editor textarea: min 48px height, visible label
  - Comment form: min 44x44px buttons, floating labels avoided
  - Test with actual mobile device (not just browser DevTools)
- **Complexity:** Low (CSS/HTML fixes)
- **Recommendation:** Include in v1.1 bug fixes sprint
- **Confidence:** MEDIUM—empirical across civic platforms

#### 2. **Markdown rendering performance with large comments**
- **Common issue:** Real-time preview slows down when parsing 5000+ character comments
- **Why it happens:** Marked.js is fast but naive rendering of large strings
- **Prevention:**
  - Debounce preview updates (wait 500ms after user stops typing)
  - Memoize parsed output (don't re-render if Markdown unchanged)
  - Test with pathological input (deeply nested lists, large code blocks)
- **Complexity:** Low to Medium (debouncing, memoization)
- **Recommendation:** Include if implementing live preview (Option: defer)
- **Confidence:** HIGH—published research on Markdown rendering

#### 3. **XSS via Markdown links**
- **Common issue:** User pastes malicious link `[click me](javascript:void(0))`
- **Why it happens:** Marked.js allows dangerous protocols by default
- **Prevention:**
  - DOMPurify config: whitelist only `http:` and `https:` protocols
  - Test with payloads like `javascript:`, `data:`, `vbscript:`
  - Verify server-side sanitization (not just client-side)
- **Complexity:** Low (DOMPurify config)
- **Recommendation:** Add to v1.1 test suite
- **Confidence:** HIGH—CVE-2025-24981 recent example

#### 4. **Comment threading edge cases**
- **Common issue:** Replies to deleted comments, deep nesting exceeding limits
- **Why it happens:** Cascade delete and depth limits sometimes overlooked
- **Prevention:**
  - Test deletion of middle comment (replies should still render)
  - Test max depth enforcement (try to reply at level 11)
  - Verify orphaned replies render gracefully
- **Complexity:** Low (existing code already handles)
- **Recommendation:** Add integration tests for v1.1
- **Confidence:** HIGH—git history shows depth limit already implemented

#### 5. **Vote count stale updates**
- **Common issue:** User votes, count doesn't update until page refresh
- **Why it happens:** Client-side state not synced with server response
- **Prevention:**
  - Ensure vote endpoint returns updated `net_votes` count
  - Update local component state immediately after vote
  - Test rapid consecutive votes
- **Complexity:** Low (already implemented in v1.0)
- **Recommendation:** Include regression tests
- **Confidence:** HIGH—v1.0 tests confirm this works

### Civic Platform Pitfalls (Empirical from Decidim/Consul)

Research into Decidim and Consul platforms reveals these domain-specific issues:

#### 1. **Comment moderation at scale**
- **Issue:** With 100+ ideas and 1000+ comments, moderation queue overflows
- **Not a v1.1 problem yet** (small user base), but plan for v1.2
- **Recommendation:** v1.1 should log all comment creation for future moderation UI

#### 2. **Category/search relevance over time**
- **Issue:** As ideas pile up, sorting by recency becomes useless (newest floats, old ideas forgotten)
- **Not in v1.0 scope** (no categories/search), but Markdown will exacerbate
- **Recommendation:** v1.1 should document limitation; categorization is v2 priority

#### 3. **Double voting via back-button**
- **Issue:** User votes, hits back, votes again (impression of multiple votes)
- **Root cause:** Browser caching + stateless API
- **Prevention:** v1.0 already handles via email-based uniqueness; v1.1 should test
- **Complexity:** Already solved
- **Confidence:** HIGH
