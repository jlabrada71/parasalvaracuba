## Architecture Changes Made

### Before (Broken)
```
API: ON CONFLICT (idea_id, comment_id, email) DO UPDATE
Problem: Doesn't work for idea votes where comment_id = NULL
```

### After (Working)
```
API: Check if exists → UPDATE or INSERT
- Idea votes: Check (idea_id, email)
- Comment votes: Check (idea_id, comment_id, email)
Database: Indexes only, no uniqueness constraints
```

## Design Decision Rationale

**Why app-level uniqueness instead of database constraints?**
- PostgreSQL's NULL semantics don't work well with the mixed idea_id/comment_id schema
- Trying to enforce uniqueness at database level created endless constraint conflicts
- App-level check-and-update is simpler, more maintainable, and battle-tested pattern
- Trade-off: Slightly less database protection, but easier to maintain and understand

**Why refetch instead of local state update?**
- Ensures UI always shows server's source of truth
- Prevents stale data from manual edits or other sessions voting
- Simple to implement and debug

Rather than fighting the database, we simplified to let the application handle uniqueness via explicit logic. This is cleaner, more understandable, and actually more reliable than trying to work around NULL semantics in constraints.
